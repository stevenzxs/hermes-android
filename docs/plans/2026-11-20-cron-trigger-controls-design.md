# Cron 触发控制设计

## 目标与事实

改善拒绝原因、可编辑触发规则及防重复点击。线上任务 `150-upgrade-aux-reasoning` / `e8a76fd0e253` 已完成 1/1 次，state=completed、fire_claim=null；后续两次 claim 被拒绝，并非运行锁残留。线上检查只读，本设计不授权重跑该任务。

## 已批准契约

- 触发方式（定时/仅手动）与执行上限（不限/1/N）独立。
- 定时规则支持现有指定时间、间隔和 Cron 表达式，保留时区语义。
- 修改设置不启动执行，不自动解除暂停或终态；下一次定时执行只针对用户明确启用的任务。
- 已完成任务必须显式确认“开启新一轮执行”，保留原任务及执行历史；开启后不立即执行。建议创建新的后继任务 ID，并携带前轮关联，不清空原记录计数。
- 仅手动模式由服务端保证，定时器/外部定时回调不能执行；不能用暂停伪装该模式。
- 错误返回稳定 code/message，旧客户端 detail 保持字符串；无法证明竞争方时不声称“其他调度器接管”。
- Android 保留服务端原因；未知响应退回 HTTP 状态，不显示原始 HTML/凭据。
- 同一连接、profile、任务的并发点击只发出一次请求。跨设备并发仍由服务端原子 claim 防护。
- 超时意味着结果未知，先核对状态/记录，不自动重试 POST。刷新失败不抹掉已确认的触发结果。

## 架构

复用 cron 存储锁、provider 执行路径及 Dashboard REST；新增行为置于主题 sibling，不扩充 jobs.py 大文件。手动模式采用可选 trigger_mode=scheduled|manual，旧记录缺失时按 scheduled 解读。模式必须贯穿存储、定义导入、next_run 推导、due 扫描、provider 注册和外部回调；manual 任务 next_run_at=null，但显式授权的手动 fire 可 claim 并计入本轮上限。

拒绝原因须来自同一原子 admission 判定；请求前读取可用于 UI，但不得取代原子保护。兼容 provider 不提供细分原因时返回通用 claim_conflict，不能推测。

Android Classic 与 NextGen 共用触发控制及错误解析；编辑器保存时回读模式、规则、上限。新服务端显式声明能力，旧服务端不支持时隐藏新模式/重开入口并说明原因，拒绝静默降级。

## 边界与风险

“新一轮”创建后继任务须防重复创建，绑定 profile/原任务/请求 ID，并在原子存储事务下处理；原任务仍可查历史。新一轮默认未启用，用户另行启用定时或点击手动触发。有限次数必须按现有 scheduler 的 occurrence 计数规则验证，不能假设任何手动 off-tick 都会递增旧 repeat 计数（cron/extra_fire.py 有特殊规则）。

不改变模型、审批、部署权限、签名或生产任务。实现不代表构建/发布；不在服务器编译、不清线上锁、不自动调度 Actions。

## 验收

覆盖：终态准确拒绝；真实运行占用；未取得 claim 的通用原因；旧错误体；快速双击；连接/profile 切换后的旧响应；超时结果未知；编辑不执行；手动任务在 tick/外部 callback 下均不执行；显式手动计数；1/N 次耗尽；并发开启新轮只创建一条；原历史完整；旧记录默认值及旧客户端兼容。
